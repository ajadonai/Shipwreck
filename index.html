Security

11 ways to get owned

01
Auth tokens stored in localStorage
One XSS attack → every user account compromised
Critical
Why this matters
localStorage is accessible to any JavaScript running on your page. If an attacker injects a script (XSS), they can steal every user's token and impersonate them indefinitely.
The fix
  • Use httpOnly cookies for session tokens — JavaScript can't access them
  • Set Secure and SameSite=Strict flags
  • If you must use localStorage, implement token rotation and short expiry
⚡ Quick fix — 30 min
02
No input sanitisation on forms
SQL injection still works in 2026. Your AI didn't tell you that.
Critical
Why this matters
Unsanitized input lets attackers inject malicious SQL, JavaScript, or commands. They can dump your database, delete records, or escalate privileges.
The fix
  • Use parameterized queries or an ORM — never concatenate user input into SQL
  • Validate and sanitize all input on the server side
  • Escape output when rendering user content in HTML
🔧 Moderate — 2-4 hours
03
Hardcoded API keys in the frontend
Someone will find them within 48 hours of launch
Critical
Why this matters
Frontend code is fully visible to users. Bots scrape GitHub and npm packages for exposed keys. Your API bill or data breach is one Ctrl+U away.
The fix
  • Move sensitive API calls to a backend proxy
  • Use environment variables on the server
  • If client-side keys are necessary (e.g., analytics), use restricted keys with domain locking
🔧 Moderate — 1-2 hours
04
Stripe webhooks with no signature verification
Anyone can fake a successful payment event
Critical
Why this matters
Without verifying the webhook signature, an attacker can POST fake events to your endpoint, granting themselves premium access or marking orders as paid.
The fix
  • Always use stripe.webhooks.constructEvent() to verify signatures
  • Store your webhook secret in environment variables
  • Return 400 for invalid signatures; log the attempt
⚡ Quick fix — 15 min
05
Sessions that never expire
Stolen token = permanent access. Forever.
High
Why this matters
Long-lived tokens give attackers unlimited time to exploit a stolen credential. Even after a user changes their password, the old token works.
The fix
  • Set short access token expiry (15-60 min)
  • Use refresh tokens for seamless re-auth
  • Invalidate all sessions on password change
  • Implement absolute session timeout (e.g., 30 days max)
🔧 Moderate — 2-3 hours
06
Password reset links that don't expire
Old email in someone's inbox = instant account takeover
High
Why this matters
If someone gains access to a user's email (phishing, shared computer, breach), every valid reset link is an open door to their account.
The fix
  • Expire reset tokens after 15-60 minutes
  • Invalidate token after single use
  • Invalidate all reset tokens when password is changed
  • Use cryptographically secure random tokens
⚡ Quick fix — 30 min
07
No CORS policy
Any website on the internet can make requests to your API
High
Why this matters
Without CORS restrictions, malicious sites can make authenticated requests using your users' cookies, stealing data or triggering actions on their behalf.
The fix
  • Configure Access-Control-Allow-Origin to your specific domains
  • Never use * with credentials
  • Whitelist only the origins you control
⚡ Quick fix — 15 min
08
Admin routes with no role checks
Any logged-in user can access your admin panel
Critical
Why this matters
Authentication ≠ Authorization. Just because someone is logged in doesn't mean they should access admin functions. This is called Broken Access Control — OWASP's #1 vulnerability.
The fix
  • Implement role-based access control (RBAC) on every protected route
  • Check permissions server-side, not just in the UI
  • Use middleware to enforce authorization consistently
  • Audit access logs regularly
🔧 Moderate — 2-4 hours
09
No CSRF protection on state-changing endpoints
Any malicious site can trigger actions as your logged-in users
High
Why this matters
Cross-Site Request Forgery tricks browsers into making authenticated requests. A hidden form on a malicious site could transfer funds, change settings, or delete accounts.
The fix
  • Use CSRF tokens on all state-changing requests
  • Set SameSite=Strict or Lax on cookies
  • Verify the Origin header on requests
  • Most frameworks have built-in CSRF protection — enable it
🔧 Moderate — 1-2 hours
10
Secrets committed to git history
Even if you delete them — they're in the commit log forever
Critical
Why this matters
Git remembers everything. Even "deleted" secrets live in your repo history. Bots scan GitHub constantly for leaked credentials — they'll find yours.
The fix
  • Use .env files and add them to .gitignore before first commit
  • Use git-secrets or gitleaks to prevent accidental commits
  • If leaked: rotate the secret immediately, then rewrite history with git filter-branch or BFG Repo-Cleaner
  • Use a secrets manager (Vault, AWS Secrets Manager, etc.) for production
🔨 Involved — If already leaked
11
No Content Security Policy headers
Opens the door to XSS, clickjacking, and data exfiltration
High
Why this matters
CSP tells browsers which sources of content are trusted. Without it, injected scripts run freely, iframes can overlay your UI, and data leaks to attacker domains.
The fix
  • Add Content-Security-Policy header
  • Start with report-only mode to find violations
  • Restrict script-src, style-src, frame-ancestors
  • Also add X-Frame-Options and X-Content-Type-Options
🔧 Moderate — 1-2 hours

Infrastructure

10 ways to go down

12
No rate limiting on API routes
Anyone can spam your backend into a $500 bill overnight
High
Why this matters
Without rate limits, a single script can hammer your API endlessly. DDoS, credential stuffing, resource exhaustion — all trivially easy.
The fix
  • Implement rate limiting at the API gateway or app level
  • Use sliding window or token bucket algorithms
  • Set different limits per endpoint (auth endpoints need stricter limits)
  • Return 429 Too Many Requests with Retry-After header
🔧 Moderate — 1-2 hours
13
No database connection pooling
First traffic spike = database crashes
High
Why this matters
Opening a new database connection for every request is expensive. Under load, you exhaust connection limits, and the database stops accepting new connections.
The fix
  • Use a connection pooler like PgBouncer (Postgres) or built-in ORM pooling
  • Configure pool size based on your database's max connections
  • For serverless: use a managed pooler or connection proxy
  • Monitor active connections and tune limits
🔧 Moderate — 1-2 hours
14
Images uploaded directly to your server
No CDN = 8-second load times + massive hosting bill
Medium
Why this matters
Serving images from your app server blocks resources, increases latency for distant users, and scales terribly. One viral post and you're down.
The fix
  • Upload to S3, Cloudflare R2, or similar object storage
  • Put a CDN in front (CloudFront, Cloudflare, etc.)
  • Resize and optimize images on upload
  • Use signed URLs if access control is needed
🔨 Involved — 4-8 hours
15
Emails sent synchronously in request handlers
One slow SMTP server = your entire app hangs
Medium
Why this matters
Email delivery can take seconds and fail randomly. Blocking on email means slow page loads and cascading failures when email providers hiccup.
The fix
  • Queue emails for async processing (Redis, SQS, etc.)
  • Return success immediately, process in background
  • Implement retry logic with exponential backoff
  • Monitor queue depth and delivery rates
🔧 Moderate — 2-3 hours
16
No health check endpoint
Your app goes down silently. You find out from a client.
High
Why this matters
Load balancers, orchestrators, and monitoring systems need a way to know if your app is healthy. Without it, they route traffic to dead instances.
The fix
  • Create a /health or /ready endpoint
  • Check critical dependencies (database, cache, external services)
  • Return appropriate status codes (200 healthy, 503 unhealthy)
  • Configure load balancer to use health checks for routing
⚡ Quick fix — 20 min
17
No logging in production
When something breaks you have zero idea where or why
High
Why this matters
Without structured logging, debugging production issues becomes guesswork. You'll spend hours reproducing bugs that logs would explain in seconds.
The fix
  • Use structured logging (JSON) with consistent fields
  • Include request IDs for tracing across services
  • Log at appropriate levels (error, warn, info, debug)
  • Ship logs to a central service (Datadog, Logtail, etc.)
  • Set up alerts on error spikes
🔧 Moderate — 2-3 hours
18
No environment variable validation at startup
App silently breaks in production with zero error message
Medium
Why this matters
Missing or malformed env vars cause cryptic failures deep in your code. You'll chase ghosts before realizing DATABASE_URL was never set.
The fix
  • Validate all required env vars at startup, before handling requests
  • Use a schema validator (Zod, envalid, etc.)
  • Fail fast with clear error messages
  • Document all required variables in your README
⚡ Quick fix — 30 min
19
No graceful shutdown handling
Deploy mid-request → half-completed transactions
Medium
Why this matters
When your app receives SIGTERM, killing it immediately leaves requests incomplete, database transactions uncommitted, and users confused.
The fix
  • Handle SIGTERM: stop accepting new requests, finish existing ones
  • Set a shutdown timeout (e.g., 30s max)
  • Close database connections and flush logs
  • Return 503 to load balancer health checks during shutdown
🔧 Moderate — 1-2 hours
20
No retry logic with backoff on external API calls
One flaky third-party service takes your whole app down
High
Why this matters
External services fail. A lot. Without retries, transient failures become hard errors. Without backoff, you amplify the problem by hammering failing services.
The fix
  • Implement exponential backoff with jitter
  • Only retry idempotent operations or use idempotency keys
  • Set max retry limits to avoid infinite loops
  • Consider circuit breaker patterns for persistent failures
🔧 Moderate — 1-2 hours
21
No request timeout on outbound calls
One hung dependency → your entire thread pool is gone
High
Why this matters
Without timeouts, requests to slow services wait forever. All your workers get stuck waiting, and new requests queue up until everything grinds to a halt.
The fix
  • Set explicit timeouts on all HTTP clients
  • Use separate connect and read timeouts
  • Fail fast — a 5s timeout is usually better than waiting 60s
  • Monitor timeout rates as a signal of dependency health
⚡ Quick fix — 30 min

Data

6 ways to lose everything

22
No database indexing on queried fields
Works fine at 100 users. Completely dies at 1,000.
High
Why this matters
Without indexes, every query scans every row. That 10ms query at 100 rows becomes a 10-second query at 100,000 rows. Your users will notice.
The fix
  • Add indexes on columns used in WHERE, JOIN, and ORDER BY
  • Use EXPLAIN ANALYZE to understand query plans
  • Index foreign keys
  • Consider composite indexes for multi-column queries
  • Don't over-index — each index slows writes
🔧 Moderate — 1-2 hours
23
No pagination on database queries
One fetch loads your entire database into memory
High
Why this matters
Fetching unbounded results crashes servers, times out requests, and creates terrible UX. Works in dev with 10 records; explodes in prod with 10 million.
The fix
  • Always use LIMIT/OFFSET or cursor-based pagination
  • Set sane defaults (20-50 items per page)
  • Implement cursor pagination for large datasets (offset is slow at high values)
  • Return pagination metadata (total count, next cursor, etc.)
🔧 Moderate — 1-2 hours
24
No backup strategy on your database
One bad migration = all your user data. Gone.
Critical
Why this matters
Databases fail. Humans make mistakes. Ransomware exists. Without tested backups, you're one DROP TABLE away from catastrophe.
The fix
  • Enable automated daily backups (most managed DBs have this)
  • Use point-in-time recovery if available
  • Test your restore process regularly
  • Keep backups in a different region/account
  • Document your recovery runbook
🔧 Moderate — 2-3 hours
25
No soft deletes
User clicks delete → data is actually gone. No recovery. No audit trail.
Medium
Why this matters
Hard deletes are permanent and break referential integrity. Users accidentally delete things. Legal/compliance often requires retention. You'll wish you had an undo button.
The fix
  • Add a deleted_at timestamp column
  • Filter out soft-deleted records in queries by default
  • Implement a "trash" UI for recovery
  • Schedule permanent deletion after a retention period
  • Maintain foreign key relationships even when soft-deleted
🔧 Moderate — 2-4 hours
26
No created_at / updated_at timestamps
You will need these. Retrofitting them is painful.
Medium
Why this matters
Timestamps are essential for debugging, auditing, sync logic, cache invalidation, and sorting by recency. Adding them later requires migrations and backfills.
The fix
  • Add created_at and updated_at to every table from day one
  • Use database-level defaults and triggers to auto-set them
  • Index created_at for time-based queries
  • Consider deleted_at for soft deletes
⚡ Quick fix — 15 min per table
27
Database migrations with no rollback plan
One broken migration → you're stuck in a broken state
High
Why this matters
Migrations fail partway. New columns break old code. You need to be able to roll back safely, or you'll be debugging production at 2am with no exit strategy.
The fix
  • Write reversible migrations with up() and down() methods
  • Test rollbacks in staging before production
  • Make migrations backward-compatible (expand/contract pattern)
  • Take a backup before running destructive migrations
  • Never delete columns or tables in the same deploy as code changes
🔨 Involved — Requires discipline

Code Quality

7 ways to build on sand

28
No error boundaries in the UI
One crash = white screen = user never comes back
High
Why this matters
One uncaught exception in React unmounts your entire app. A white screen is worse than a partial failure — users think your site is down.
The fix
  • Wrap key UI sections in Error Boundaries
  • Show a friendly fallback UI instead of crashing
  • Log errors to an error tracking service
  • Offer users a way to retry or report the issue
🔧 Moderate — 1-2 hours
29
No TypeScript on AI-generated code
AI writes confident, wrong, untyped code — and you ship it anyway
High
Why this matters
AI confidently hallucinates incorrect code. Without types, runtime errors surface only when users hit them. TypeScript catches mistakes at compile time.
The fix
  • Use TypeScript with strict mode enabled
  • Define types for all API responses and database models
  • Don't use any as an escape hatch
  • Validate external data with Zod or similar
  • Treat type errors as bugs, not annoyances
🔨 Involved — Requires migration
30
Trusting client-side validation only
Anyone with curl can bypass every rule in your form
Critical
Why this matters
Client-side validation is for UX, not security. Attackers bypass it trivially by editing JavaScript or sending raw HTTP requests.
The fix
  • Always validate on the server — never trust client input
  • Use the same validation schema on client and server (Zod works both places)
  • Validate types, formats, lengths, and business rules
  • Client validation is a UX enhancement, not a security measure
🔧 Moderate — 2-3 hours
31
No CI/CD pipeline
You're deploying from your laptop and hoping for the best
Medium
Why this matters
Manual deploys are error-prone. "Works on my machine" isn't good enough. You need automated builds, tests, and deployments for reliability.
The fix
  • Set up GitHub Actions, GitLab CI, or similar
  • Run tests and lint on every push
  • Auto-deploy to staging on merge to main
  • Use preview deployments for PRs
  • Require passing CI before merge
🔧 Moderate — 2-4 hours
32
No tests on critical paths
Payment, auth, signup — one regression = you're losing money
High
Why this matters
Breaking checkout costs money. Breaking auth leaks data. You don't need 100% coverage — but the paths that make you money need tests.
The fix
  • Write integration tests for auth flows (signup, login, password reset)
  • Test payment flows end-to-end with Stripe's test mode
  • Add smoke tests for critical API endpoints
  • Don't test everything — test what matters most
🔨 Involved — 4-8 hours
33
Console.log as your debugging strategy
Works locally. Tells you nothing in production.
Medium
Why this matters
Console.log doesn't persist, doesn't structure, doesn't alert. Production bugs need context, stack traces, and history — not ephemeral print statements.
The fix
  • Use a proper logging library (pino, winston, etc.)
  • Add error tracking (Sentry, Bugsnag, etc.)
  • Learn browser DevTools (breakpoints, network tab, profiler)
  • Use structured logs with context (user ID, request ID, etc.)
🔧 Moderate — 2-3 hours
34
No dependency pinning
A patch update to a transitive dep breaks your build on Saturday night
Medium
Why this matters
Unpinned dependencies install the latest version at build time. A bad release to any package in your tree can break your app without you changing anything.
The fix
  • Commit your lockfile (package-lock.json, yarn.lock)
  • Use exact versions for critical dependencies
  • Use Dependabot or Renovate for controlled updates
  • Test updates in CI before merging
⚡ Quick fix — 10 min

UX

3 ways to lose every user

35
No loading states
User clicks, nothing happens, clicks 5 more times — 5 duplicate requests fire
High
Why this matters
Without feedback, users assume their click didn't register. Multiple clicks create duplicate submissions, race conditions, and confused users.
The fix
  • Show loading spinners immediately on action
  • Disable buttons while requests are in flight
  • Use skeleton screens for page/section loads
  • Implement optimistic UI where appropriate
  • Add debouncing to prevent duplicate submissions
🔧 Moderate — 2-3 hours
36
No error handling on network failures
Long form, hit submit, connection drops — everything is lost
High
Why this matters
Network failures happen. Phones go through tunnels. Wifi drops. Silent failures are maddening — users don't know if their action succeeded or failed.
The fix
  • Catch errors and show clear error messages
  • Offer retry buttons for failed requests
  • Auto-save form progress to localStorage
  • Detect offline state and inform users
  • Queue actions for retry when connection returns
🔧 Moderate — 2-4 hours
37
No mobile responsiveness
Half your traffic bounces immediately
Critical
Why this matters
Over 50% of web traffic is mobile. A desktop-only layout means horizontal scrolling, tiny tap targets, and users leaving for a competitor that works on their phone.
The fix
  • Design mobile-first, then scale up
  • Use responsive breakpoints (Tailwind, media queries)
  • Test on real devices, not just browser DevTools
  • Ensure tap targets are at least 44x44px
  • Simplify navigation for small screens
🔨 Involved — Varies by scope
